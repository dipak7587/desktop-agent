# Tools

The **Tools** sidebar creates local LangChain tools. Choose **New tool** to open **Builder**
and **TypeScript** tabs in the existing editor. Tools stay separate from Skills, Knowledge Base,
Agents, MCP, and Workflows. An agent selects a saved tool; its configuration does not contain a
copy of the tool implementation.

## Builder

Enter **Name** and **Description**. Names use letters, numbers, and underscores without spaces;
start with a letter or underscore. Lowercase names such as `run_command` are recommended.
Describe when the model should call the tool. **Tool Type** currently offers **LangChain**.

Under **Input Schema**, use **+ Add Input** and configure each parameter's name, type,
description, required flag, and optional default. Parameter names must be unique. Types are
`string`, `number`, `boolean`, `array`, `object`, `enum`, `date`, and `any`; the default is `string`.
Enter enum choices one per line. Default values use JSON: `20`, `false`, `"."`, `[]`, or `{}`.
Date defaults use an ISO date string. Arrays generated by the Builder accept any item type;
use TypeScript for typed arrays and nested object schemas.

**Function Logic** is an async function body. Input names are available as variables. Return the
result, and use the starter comment `// Start coding from here.` as the insertion point. The
example dropdown includes a working calculator and a search-files template. The search template
returns an empty result list until you implement actual searching.

The Builder generates real LangChain TypeScript with one `tool()` and a Zod object schema:

```ts
import { tool } from 'langchain/tools';
import { z } from 'zod';

export const customTool = tool(
  async (__toolInput) => {
    const { a, b, operation } = __toolInput;
    // Start coding from here.
    switch (operation) {
      case 'add':
        return a + b;
      case 'subtract':
        return a - b;
      case 'multiply':
        return a * b;
      case 'divide':
        if (b === 0) throw new Error('Cannot divide by zero');
        return a / b;
    }
  },
  {
    name: 'calculator',
    description: 'Perform a basic arithmetic operation.',
    schema: z.object({
      a: z.number().describe('First number'),
      b: z.number().describe('Second number'),
      operation: z.enum(['add', 'subtract', 'multiply', 'divide']),
    }),
  },
);
```

Optional values generate `.optional()`; defaults generate `.default(...)`; descriptions generate
`.describe(...)`. Objects generate `z.record(z.string(), z.any())`, arrays generate
`z.array(z.any())`, and dates generate `z.date()`.

## TypeScript editor and validation

Paste complete TypeScript in the **TypeScript** tab. Export exactly one named LangChain `tool()`.
Import `tool` from `langchain/tools`, `langchain`, or `@langchain/core/tools`, and `z` from `zod`.
The editor has syntax highlighting, line numbers, a separate code preview, native copy/paste/select-all/undo/redo,
**Format TypeScript**, **Validate**, and **Copy TypeScript**. Formatting uses the TypeScript AST
printer and preserves comments and source statements.

**Validate** checks TypeScript syntax, installed imports, exported `tool()`, the implementation,
name, description, schema structure, duplicate parameters, types, enum values, and defaults.
Errors appear at the top of the editor. Imports must be installed application packages or Node
built-ins; relative imports, absolute imports, and remote imports are unsupported. Validation is
static: it does not type-check arbitrary application code or execute module statements, schema
callbacks, tool functions, or imports. Runtime Zod validation still occurs on invocation.

Supported static Zod expressions include primitive schemas, objects, records, arrays, enums,
literals, unions, optional/nullable values, defaults, descriptions, numeric bounds, integer and
positive constraints, and strict/passthrough objects. Function-based refinements and transforms
are preserved for runtime execution. Unsupported schema expressions report an actionable error
rather than executing them to discover their meaning.

Switching to **Builder** uses the TypeScript AST to recover simple input schemas and function
bodies. Advanced code, helper declarations, extra imports/options, typed arrays, nested objects,
and schema constraints remain in **Advanced TypeScript mode**; the editor preserves the complete
source instead of regenerating and losing code.

## Import and convert

**Import Tool** reads `.ts`, `.md`, `.json`, `.yaml`, and `.yml`, detects the format, and opens a
TypeScript preview before saving. **Paste definition** provides the same conversions for pasted
text. All formats use one generator and static validator. Conversion does not execute code.

JSON example:

```json
{
  "name": "add_numbers",
  "description": "Add two numbers",
  "input": {
    "a": { "type": "number", "required": true },
    "b": { "type": "number", "required": true }
  },
  "function": "return a + b;"
}
```

YAML example:

```yaml
name: get_weather
description: Get weather information
input:
  city:
    type: string
    required: true
    description: City name
  units:
    type: string
    required: false
    defaultValue: metric
function: |
  return { city, units };
```

Markdown example:

```md
# Tool

Name: get_time

Description:
Return the current time for a timezone.

## Input

timezone:

- type: string
- required: true
- description: IANA timezone

## Function

return { timezone, value: new Date().toISOString() };
```

Markdown may also use YAML frontmatter with `name`, `description`, and `input`; the body contains
function logic. JSON/YAML accept `inputs` arrays or an `input` object, and `functionBody` or
`function` for the function body.

## Save, load, and existing tools

**Save Tool** validates and persists executable TypeScript in the existing directory:
`<userData>/tools/<id>.ts`. Stable IDs follow the existing app convention so agent references
remain valid. App metadata (group, enabled state, timestamps, and ID) is stored in an inert
`// @workspace-tool ...` comment. The remaining file is a normal executable LangChain module.
Executable tools are not saved as JSON, YAML, or Markdown. Export produces the same `.ts` file.
Discovery reads saved modules statically; it never imports or executes them while listing tools.

Existing Markdown JavaScript/API tools remain readable. Saving an existing tool converts its
file to TypeScript under the same ID and removes the old Markdown file only after the new file
is written successfully. Existing JavaScript receives its `input` and `require` contract;
existing API calls retain HTTP methods, credential references, response limits, and redaction.

## Test and run

**Test Tool** in the editor opens an isolated test section for unsaved source. Enter a JSON object
matching the schema and choose **Run test**. The dialog reports execution status, output, errors,
and duration. The existing library **Test / Run** action tests saved tools. Date inputs may use
ISO strings, which are converted to Date instances before invocation.

Only explicit testing or an approved agent invocation executes code. TypeScript is transpiled
in the main service and loaded in the existing separate Node process, then invoked through the
exported LangChain tool's `.invoke(input)`. The original Zod schema handles runtime validation,
defaults, and constraints. The test service does not write temporary executable definitions.

The existing timeout, cancellation, three-tool concurrency limit, reduced child environment,
100 KB input/output limits, and secret redaction remain active. Imported code is trusted local
code running with the user's privileges; process separation is not an OS sandbox. Testing
explicitly authorizes execution, including module initialization. Closing an editor does not
cancel a running test. API tools reject redirects and embedded URL credentials.

## Use from an agent

Select enabled tools in **Agents → Tools**. References remain `custom:<tool-id>`. The agent receives
the tool description and its derived JSON input schema; it invokes the saved source through the
existing capability service. Custom Tool calls require approval by default, including global
full-auto mode, unless a per-capability Always allow permission applies. No editor, import,
conversion, validation, preview, or registry operation bypasses this approval path.

Inputs, outputs, failures, and approvals remain in persistent [execution history](AGENTS.md#execution-history).
Tools can be called without a project folder; when selected, the folder is the child process's
working directory. It is not a security sandbox.

Deletion requires confirmation and remains blocked while any agent references the tool,
including disabled agents. Groups and existing import/export, backup, and selection flows retain
stable tool IDs.

See [Agents](AGENTS.md), [Security](SECURITY.md), and [Capability decisions](CAPABILITIES.md).
